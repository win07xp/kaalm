# Scenario coverage

The [acceptance scenarios](scenarios.md) S1 to S25 are the definition of
"done". This page maps each scenario to the implemented behavior
that exercises it and the automated tests that verify it, so the acceptance
surface is auditable rather than aspirational.

Coverage is one of three kinds:

- **Unit and integration**: a Go or Python test in the repository asserts the behavior directly. Go tests run with `make test` (or `make cover-check`, the CI coverage check) and `make runtime-test` for the agentruntime module and the Go starter; the Python base image suite runs with `make python-test`.
- **Envtest**: a controller-runtime test against a real apiserver asserts the
  reconciler behavior; `make test` runs these too.
- **End-to-end (e2e)**: a Ginkgo spec runs against a real k3d cluster with the
  chart installed and the real binaries, and asserts the behavior end to end.
  This is the strongest kind: it exercises the kubelet, real garbage
  collection, cert-manager, and kube-router that the lighter kinds cannot.
  `make e2e` recreates the cluster, builds and imports the images, installs
  the chart, and runs the suite; CI runs it on every PR. `make e2e-cilium`
  recreates the cluster with Cilium in place of flannel and runs the FQDN
  egress spec, which flannel cannot enforce; CI runs it when the FQDN policy
  path changes. `make e2e-kata` recreates the cluster with the Kata runtime
  and runs the MicroVM spec. It needs `/dev/kvm` and a Kata release unpacked
  at `/opt/kata`, and CI does not run it. kata-deploy cannot install into a
  k3d node, which runs k3s without systemd, so the target mounts the host's
  Kata release and a containerd drop-in into the nodes and enlarges the
  nodes' `/dev/shm`.

The e2e column is the acceptance surface: every scenario names the spec that proves it on a cluster, and every spec passes. S1 to S20 and S22 to S25 run in `test/e2e/` (build tag `e2e`) against the locally built chart and images. S21 runs in `test/upgrade/` (build tag `upgrade`, `make e2e-upgrade`), which starts from the previous released chart; its CI workflow runs on every release PR, and a release is tagged only after it passes there ([RELEASING.md](https://github.com/win07xp/kaalm/blob/main/RELEASING.md) describes the procedure). It also runs on a release from a tag pushed by hand, and on pull requests that touch the API, the CRDs, the migrator, or the suite itself. The LLM scenarios run against an in-cluster mock provider that speaks both the Anthropic and the OpenAI formats, and the channel scenarios against a mock of each platform's API.

The S6 NetworkPolicy behavior is also exercised by the `Golden path` deny probe, which proves a Pod in `default` cannot reach the agent Service.

Two scenarios keep a scope note: their e2e spec proves the Kaalm-owned
primitive, but part of the scenario is outside the code's test surface.

- **S2**: k3d installs no gVisor `RuntimeClass`. The default e2e test proves the reconciler's part (the class `runtimeClassName` reaches the Pod spec, a missing `RuntimeClass` leaves the Agent `PodCreateRejected`, and the image allowlist rejects a disallowed image). The Kata VM boundary is proven by the `MicroVM isolation on Kata` spec under `make e2e-kata`: a resident agent passes its probes and carries the RuntimeClass overhead, a task boots its own guest kernel and uses its PVC and TLS files over virtio-fs, the NetworkPolicy still denies a Pod in another namespace, and a hibernated agent wakes. The sandbox-escape property is the cluster's ([Workload isolation](../security/threat-model.md#workload-isolation)).
- **S9**: k3d's local-path provisioner has no snapshot support. The e2e proves `existingClaim` adoption and read-back; the snapshot step is documented on [S9](scenarios.md#s9-promote-a-task-agent-to-persistent-for-human-takeover).
