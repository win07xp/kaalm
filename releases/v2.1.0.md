Kaalm 2.1.0 is a minor release on 2.0.1. It adds the `kaalm` agent skill, a values schema for the Helm chart, a cap on messages waiting for an Agent's Pod, and Secret watching that re-runs Agents and AgentTasks as soon as a Secret changes. The upgrade is in place: apply the CRDs, then run `helm upgrade`, as [Upgrading Kaalm](https://github.com/win07xp/kaalm/blob/v2.1.0/guide/src/getting-started/upgrading.md) describes. The CRDs and the API do not change.

One change can fail an upgrade that worked before. The chart now ships `values.schema.json`, and Helm rejects a values file with a misspelled key, a value of the wrong type, or a malformed RBAC subject, where it used to ignore or misrender it. Before you upgrade, run your usual `helm upgrade` command with `--version 2.1.0` and `--dry-run`. It changes nothing and names any rejected value. You can also run `helm lint` on the 2.1.0 chart with `-f` and your values file. See [Values are checked before they render](https://github.com/win07xp/kaalm/blob/v2.1.0/docs/src/operations/deployment.md#values-are-checked-before-they-render).

Published artifacts, all at version `2.1.0`:

- Images: `ghcr.io/win07xp/kaalm-controller`, `kaalm-gateway`, `kaalm-console`, `kaalm-agent-python`, and `kaalm-agent-go`. The `latest` tag moves to `2.1.0`.
- Chart: `oci://ghcr.io/win07xp/charts/kaalm`.
- Go runtime module: `github.com/win07xp/kaalm/agentruntime/v2`, tagged `agentruntime/v2.1.0`.

## The kaalm agent skill

The `kaalm` skill teaches a coding agent how to use Kaalm. It checks what your setup is missing, gets you a cluster, installs Kaalm, adds a model key without the agent seeing it, deploys Agents and AgentTasks, and explains why a resource is not Ready. It adapts to how much Kubernetes you know, and it asks before every change ([#603](https://github.com/win07xp/kaalm/issues/603)).

In Claude Code, add the marketplace at this release's tag, then install the plugin:

```text
/plugin marketplace add win07xp/kaalm#v2.1.0
/plugin install kaalm@kaalm
```

For another agent, copy [`plugins/kaalm/skills/kaalm`](https://github.com/win07xp/kaalm/blob/v2.1.0/plugins/kaalm/skills/kaalm) from the `v2.1.0` tag into the agent's skills folder. See [Agent skill](https://github.com/win07xp/kaalm/blob/v2.1.0/README.md#agent-skill) in the README.

## Changes

- **Helm validates your values.** The schema types every value in `values.yaml`. Every block the chart defines rejects a key it doesn't list. Byte sizes such as `gateway.maxResponseBodyBytes` take an integer or a `Ki`, `Mi`, or `Gi` suffix, so `1MB` fails where it used to render as `0`. A duration is a string with a unit, or the integer `0`, so `30` fails. A number given as a string, such as `replicas: "3"`, fails. Values that pass through as Kubernetes objects, such as `gateway.resources`, stay open for the API server to check ([#351](https://github.com/win07xp/kaalm/issues/351)).
- **A cap on messages waiting for one Agent's Pod.** Each gateway replica holds at most `gateway.maxPodWaitsPerAgent` messages (default `100`) waiting for one Agent's Pod. The next message fails at once with `503 agent_not_ready`, which is retryable. An async webhook still answers `202`, and the result carries `agent_not_ready`. Before, valid messages to an Agent that never became reachable held gateway work without a bound. The cluster-wide cap for an Agent is the value times `gateway.replicas`. The value must be positive. See [The cap on waits per Agent](https://github.com/win07xp/kaalm/blob/v2.1.0/docs/src/gateways/user/activation-and-activity.md#the-cap-on-waits-per-agent) ([#585](https://github.com/win07xp/kaalm/issues/585)).
- **A Secret change re-runs the Agents and AgentTasks that read it.** Creating, deleting, relabeling, or editing an env Secret, or a pull Secret named on the AgentClass, takes effect at once, where it took up to 30 seconds and never for a Running Agent with idle detection off. Labeling an env Secret for the workload clears the Agent's condition immediately. A Secret change doesn't wake a hibernated Agent or restart a settled AgentTask ([#406](https://github.com/win07xp/kaalm/issues/406)).
- **Secret reads need the `list` verb.** The Roles that let the gateway and the controller read Secrets grant `list` next to `get` and `watch`. They are the gateway's Role in `kaalm-system` and the Roles the controller creates per Secret. Grants in user namespaces still name each Secret. A read made before a Role has `list` uses `get` and keeps working, so the order of the rollout does not matter ([#485](https://github.com/win07xp/kaalm/issues/485)).
- **The `kaalm_watched_secrets` metric.** It is a gauge of the Secrets a gateway or controller process watches, and the `kaalm-cluster.json` Grafana dashboard has a panel for it. See [Observability](https://github.com/win07xp/kaalm/blob/v2.1.0/docs/src/operations/observability.md) ([#485](https://github.com/win07xp/kaalm/issues/485)).
- **An Agent and an AgentTask can share a name.** An AgentTask's children carry a `.task` qualifier: NetworkPolicy `{name}.task`, Certificate `{name}.task-tls`, and CiliumNetworkPolicy `{name}.task-fqdn`. Before, the second of the two stopped at `ChildConflict`. A task that exists at the upgrade keeps its old Certificate and policies until it is deleted, and a Pod that is running keeps its certificate. A tool that looks up a task's Certificate by name needs the new name. Reading `spec.secretName` from the Certificate works for every task. An Agent given the name of a task that exists at the upgrade waits with `ChildConflict` until the task is deleted. See [Upgrading Kaalm](https://github.com/win07xp/kaalm/blob/v2.1.0/guide/src/getting-started/upgrading.md) ([#558](https://github.com/win07xp/kaalm/issues/558)).
- **`kaalm.http_client()` and `kaalm.http_async_client()` take `package="httpx2"`.** Anthropic SDK 2.0 and later accepts only `httpx2` clients. With `package="httpx2"`, the Python factories build the same certificate-rotating, trace-aware client from `httpx2`, and the base image bundles it. The default is still `"httpx"`, and the OpenAI SDK takes it, so existing handlers need no change ([#606](https://github.com/win07xp/kaalm/issues/606)).
- **Writes to the Agent's state are appended and fsynced.** Both reference runtimes append each reply and memory write to `state.log` next to `state.json` and fsync it before the call returns. The cost of a write no longer grows with the dedup window. An acknowledged reply or key survives a process or node crash. An existing `state.json` loads unchanged, so there is no migration. Keep both files when you copy or inspect the volume. See [Memory and dedup persistence](https://github.com/win07xp/kaalm/blob/v2.1.0/docs/src/runtime/base-images.md#memory-and-dedup-persistence) ([#484](https://github.com/win07xp/kaalm/issues/484)).
- **Both runtimes write only strict JSON.** `kaalm.memory.put` in Python raises `TypeError` for a value that holds `NaN`, `Infinity`, or `-Infinity`, and a handler reply that holds one is rejected before it is cached. Go's JSON parser can't read those tokens, so a Go runtime that starts on a volume holding one keeps only what it read before it. Before you switch an Agent from the Python image to the Go image, overwrite or delete any such key from the Python handler, then stop the Pod gracefully. A volume that already holds one keeps loading in the Python runtime ([#595](https://github.com/win07xp/kaalm/issues/595)).

## Fixes

- **The Go runtime refuses a reply that JSON can't encode.** A handler reply with `NaN` or `Infinity` in `Metadata`, or non-JSON bytes in `Attachments`, gets a `500` and is not cached, so the gateway redelivers it. Before, the runtime cached the reply and answered `200` with an empty body ([#600](https://github.com/win07xp/kaalm/issues/600)).
- **A Running Agent with idle detection off keeps seeing Secret changes.** The controller re-runs an Agent that reads a Secret every 27 to 33 minutes, which keeps the Secret watches open. Before, the watches stopped an hour after the Agent's last pass, and a later change, such as removing the `kaalm.io/workload-secret` label from an env Secret, went unseen ([#590](https://github.com/win07xp/kaalm/issues/590)).
- **A deleted Secret is not served from the cache.** A Secret deleted just before its watch opened stayed in the cache. The gateway stops serving a deleted credential or channel Secret on the next request, and the channels that reference it re-run at once ([#551](https://github.com/win07xp/kaalm/issues/551)).
- **A gateway rollout no longer closes idle connections that clients are about to reuse.** During the drain delay, the gateway and the console leave idle connections open and mark the responses `Connection: close` (HTTP/1.1) or send a graceful GOAWAY (HTTP/2). Before, a client that reused an idle connection could fail a POST with `server closed idle connection`. A `connection refused` or an `EOF` on a new connection is still possible. See [Client errors during a rollout](https://github.com/win07xp/kaalm/blob/v2.1.0/docs/src/operations/deployment.md#client-errors-during-a-rollout) ([#554](https://github.com/win07xp/kaalm/issues/554)).
- **A message to a hibernated Agent is delivered sooner.** The gateway connects as soon as the Agent's Pod is Ready, so a wake no longer waits out a connect that hung for up to a second. `kaalm_channel_wake_duration_seconds` has buckets every 0.25 seconds between 1 and 3 seconds, where wakes land, and every earlier boundary stays ([#572](https://github.com/win07xp/kaalm/issues/572)).
- **The Python agent answers probes while it stores a reply.** The agent writes its message cache off the event loop, so a probe, a heartbeat, or another delivery isn't blocked while a reply is fsynced ([#593](https://github.com/win07xp/kaalm/issues/593)).
- **The guide's Level 1 client reads the token on every request.** The kubelet replaces the projected gateway token before it expires. A client built once with the token as `api_key` or `auth_token` gets `401` on every call after `expirationSeconds`, until the Pod restarts. If you built a client from the old example, change it to read the token file on every request. [Framework agents](https://github.com/win07xp/kaalm/blob/v2.1.0/guide/src/developers/framework-agents.md) shows an `httpx` auth hook that does this, with `httpx2` for Anthropic SDK 2.0 and later ([#605](https://github.com/win07xp/kaalm/issues/605)).

## Smaller changes

- A task completion request with a body over 1 MiB gets `413 request_too_large`.
- A Pod wait ends at the capped `wakeTimeout`, not one poll interval after it.
- The gateway drops a deleted Agent's activity record ([#565](https://github.com/win07xp/kaalm/issues/565)).
- The controller finds an Agent's or AgentTask's own Pod through an index, so its work does not grow with the number of Pods in the namespace. An AgentChannel re-runs on an Agent change only when the Agent is created or deleted, or its `status.phase` or `spec.service.enabled` changes ([#336](https://github.com/win07xp/kaalm/issues/336)).
- If you copy the starter-go template, pin the runtime module to the version of the chart on your cluster with `go get github.com/win07xp/kaalm/agentruntime/v2@vX.Y.Z`, then run `go mod tidy`. A bare `go mod tidy` resolves the newest published module, which can be newer than the runtime your cluster runs ([#593](https://github.com/win07xp/kaalm/issues/593)).
